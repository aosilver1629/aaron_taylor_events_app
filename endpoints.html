Route Ledger

Every HTTP route the app exposes, in the order it's declared in app/main.py. For each one: what it's for, what you have to send it, and exactly how it touches the database — including the two GETs that quietly aren't read-only, and the routes that cost real money or text real people.

01
GET /health no mutation

Liveness check for Railway's health monitor (healthcheckPath in railway.json).

Required input

None.

Database

None. Returns {"status": "ok"}.
02
GET /ops/sources no mutation

Read-only visibility into the source registry — which research sources exist, what fetch/extract method each one's latest run actually used, its health status, and its last 8 runs' candidate counts. No UI; this JSON is the whole surface.

Required input

  • city query, optional
    Defaults to "sf".

Database

None — reads sources and source_runs only.
03
POST /ops/research/run real sms possible

Manual trigger for Job 1 (research). Runs the exact same run_research_job the scheduler calls every other morning — not a sandboxed dry run. Inserts whatever it finds into the real events table.

Required input

  • send_ballot query, optional
    Boolean, defaults to false. Research always runs; the real SMS ballot only goes out to Aaron and Tay if this is explicitly true.

Database

Inserts new rows into events (tags/entities/gist/confidence included), records runs into source_runs, and reads/writes taste_profiles if either profile has content. Updates the in-memory state GET /ops/research/last-run reads back.
When send_ballot=true: also inserts ballots rows and sends a real SMS via the configured provider (logged to sms_log).
04
GET /ops/research/last-run no mutation

Status and summary of the most recent research run in the current process — scheduler-triggered or manual. A lightweight “did the last run work, and what did it find” check.

Required input

None.

Database

None — reads in-memory state only.
Not durable: lives in a module-level variable in app/jobs/research_job.py; resets to “no run yet” on every restart or redeploy. For durable history, Railway's structured logs are the source of truth.
05
GET /profile/{person} writes db

Fetch a taste profile — hard_excludes, include_tags, include_entities, exemplars — for profile.html or any client.

Required input

  • person path, required
    Must be "aaron" or "tay" — anything else returns 404.

Database

This GET is not actually read-only: if the person has no row in taste_profiles yet, it's lazily inserted with all-empty defaults before the row is returned. Idempotent after the first call, not on it.
06
POST /profile/{person} writes db

Save a taste profile. This is what profile.html's Save button calls — the only route that makes a preference real. A partial update, not a replace-all: any field left out of the request body keeps its previously stored value.

Required input

  • person path, required
    Must be "aaron" or "tay", else 404.
  • hard_excludes body, optional
    List of strings; each must be a valid taxonomy tag ("top/sub"), else 400.
  • include_tags body, optional
    Same validation as hard_excludes.
  • include_entities body, optional
    List of strings, type-checked only.
  • exemplars body, optional
    List of strings; max 5, each ≤200 characters, else 400.

Database

Updates the caller's row in taste_profiles with whichever fields were present (inserts the row first if none exists). A validation failure returns 400 and writes nothing.
07
POST /profile/{person}/parse real api spend

Natural-language preference assist. Turns a free-text description — “no metal, I love Watchhouse and outdoor food markets” — into a draft profile for the client to fold into its state and review.

Required input

  • person path, required
    Must be "aaron" or "tay", else 404.
  • text body, required
    Non-empty string, else 400.

Database

None. Makes a real, billed Anthropic call but never writes taste_profiles itself — only the user's own subsequent POST /profile/{person}, after reviewing the draft, persists anything. A misparsed sentence should never silently become a hard constraint.
08
GET /profile-editor/{person} no mutation

Serves the profile.html editor page — taxonomy chips, entity list, exemplar list, natural-language box. The page's own JS reads person back out of the URL and calls the routes above on the same origin.

Required input

  • person path, required
    Must be "aaron" or "tay", else 404.

Database

None — reads profile.html off disk. (Its own later fetch to route 05 still triggers that lazy insert, just not this route.)
09
POST /sms real sms

The Twilio inbound webhook — the only route real end users actually hit. Handles opt-out/opt-in/help keywords and resolves ballot replies (“1, 3, 5” / “none” / “the market one”) against the sender's most recent ballot batch.

Required input

  • From form, required
    Sender's number. Must exactly match Aaron's or Tay's — anything else is silently dropped, no reply, no log.
  • Body form, required
    The SMS text.
  • X-Twilio-Signature header, conditional
    Verified only when live (SMS_PROVIDER=twilio, DRY_RUN=false). A bad signature returns 403 before any DB access.

Database

  1. Always: one row into sms_log for the inbound message.
  2. STOP/START/HELP-family keyword: no ballot change — just a canned reply, logged outbound.
  3. A real vote: every currently-open ballot in the sender's latest batch gets its response set to "yes" or "no" and responded_at stamped, then a confirmation SMS goes out.
  • No persisted opt-out state exists anywhere in the schema — STOP/START/HELP are canned replies only; real suppression relies on Twilio/carrier-level handling.
  • Resolving ballots here never writes to Google Calendar — a separate scheduled job does that later, once both people have said yes.
  • Only the sender's single most recent batch is ever eligible — replying against an older one is impossible by design.
